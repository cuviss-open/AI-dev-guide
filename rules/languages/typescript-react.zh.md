# TypeScript + React 规则

## 目标

本规范适用于 TypeScript + React 项目，包括 `.ts` 逻辑文件和 `.tsx` 组件文件。它也可作为 AI 协作开发时的前端代码边界规则。

## 核心原则

1. 文件必须小而清晰，一个文件只做一件事。
2. UI 与逻辑必须分离。
3. Hook 是逻辑单元，React 组件是展示单元。
4. 优先拆分，而不是堆叠。
5. 允许不完美，但禁止混乱。

每次改动都应回答：AI 能否只看 3-5 个文件完成下一次修改？如果不能，应优先拆分边界。

## 文件行数

- 目标行数：300-400 行。
- 警戒线：500 行。
- 上限：1000 行。

超过 500 行必须评估拆分；超过 1000 行默认不应作为完成状态交付。如果确实不能拆，必须说明原因和后续拆分计划。

允许特例包括 Page/Screen 级容器、高内聚复杂交互和短期过渡文件，但必须标注或说明拆分方向。

## 函数与组件

- 单函数目标：60 行以内。
- 单函数上限：80 行。
- 单组件目标：UI 加 logic 不超过 300 行。

超过限制时优先拆成 `types.ts`、`constants.ts`、领域内 `utils.ts`、`components/*.tsx`、`hooks/useXxx.ts`。

不要为了压行数制造过度抽象；拆分必须让职责更清楚。

## Hook 规则

出现以下任一情况，优先抽成 Hook：

- 使用 `useState`、`useEffect`、`useMemo`、`useRef` 等。
- 异步请求。
- 订阅、定时器、事件监听、DOM 监听等副作用。
- 多组件重复逻辑。
- 单组件状态超过 3 个。

Hook 文件命名 `useXxx.ts`，只返回数据和方法，不返回 JSX；可以组合其他 Hook；不跨领域；不负责展示结构和样式。

不要把普通纯函数伪装成 Hook。没有 React Hook 或副作用的计算函数应命名为 `calculateXxx`、`formatXxx`、`resolveXxx` 等。

## React 组件规则

`.tsx` 组件文件只做三件事：调用 Hook、组织 UI、绑定事件。

禁止组件文件承担复杂数据处理、请求逻辑、副作用细节、大段工具函数或大量业务判断。

事件处理可以在组件中轻量转发；一旦包含业务判断、异步流程或多步骤状态变更，应进入 Hook。

## 目录结构

优先按领域拆分，不按技术大杂烩拆分。

不推荐：

```text
utils/
common/
helpers/
services/
```

推荐：

```text
featureA/
  Page.tsx
  components/
    Panel.tsx
    List.tsx
  hooks/
    useFeatureAState.ts
    useFeatureAActions.ts
  types.ts
  constants.ts
  utils.ts
```

`utils.ts` 只能是当前领域内的纯函数，不得变成全局杂物箱。共享能力必须有明确领域归属。

## Hook 拆分策略

当一个文件出现以下信号，必须评估拆分：

- 超过 3 个 `useEffect`。
- 超过 5 个 `useState`。
- 逻辑明显多于 UI。

拆分方向包括状态管理、事件逻辑、副作用、请求流程、表单逻辑、弹窗状态、列表分页。复杂 `useEffect` 最后处理；先提取类型、常量、纯函数和局部 UI。

## AI 编码约束

AI 不允许：

- 以“整体优化”为理由扩大修改范围。
- 顺手重构无关结构。
- 一次改多个领域模块。
- 未经要求修改既有行为逻辑。
- 为了通过检查改动不相关文件。

AI 必须：

- 一次只处理一个明确领域。
- 修改前说明影响文件。
- 优先拆分，不堆叠。
- 保证行为不变，除非任务要求改行为。
- 运行或说明类型和构建检查。

## 拆分流程

推荐顺序：

1. 提取类型、常量和纯工具函数。
2. 提取纯 UI 组件。
3. 提取表单、弹窗、列表等局部 Hook。
4. 提取页面级 Hook。
5. 最后处理复杂 `useEffect`。

每一步都应保持行为不变，并让 diff 可审查。

## 常见交互模式

以下重复逻辑优先抽成 Hook：

- loading、request、error。
- 表单提交。
- 分页。
- 弹窗状态。
- 本地筛选和排序。
- 键盘快捷键。
- 拖拽状态。
- 轮询或订阅。

## 验证

前端代码变更至少运行项目对应的类型检查、构建或测试命令。若涉及视觉交互，优先做浏览器验证。
