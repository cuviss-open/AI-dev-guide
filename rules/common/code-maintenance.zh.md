# 代码维护规则

## 文件形态

- 优先使用小而清晰的文件。
- 先按领域拆分，再按技术拆分。
- 避免把无关行为倒进 `utils`、`helpers`、`common` 或 `misc`。
- 项目变大后，根入口文件应逐步变薄。

## 重构

只有当重构服务当前任务或移除真实维护障碍时才重构。

好的理由：

- 下一次修改必须阅读巨大且无关的文件。
- 同一行为在多处重复。
- 一个文件混合多个无关职责。
- 可把高风险副作用隔离进更清晰的边界。

不好的理由：

- 代码只是不符合个人偏好。
- 格式化会在窄任务里重写整个文件。
- 还没理解本地约定就想重命名一切。

## 验证

运行与触达范围匹配的检查。优先使用项目已有脚本，不轻易发明新流程。

如果完整检查成本过高，运行最窄的有效检查，并说明取舍。
